# OTel 追蹤處理器

`otel_traces` 處理器會快取每個 `traceId` 的根追蹤區段（root span）資訊，藉此補齊所有傳入的 OpenSearch Data Prepper 追蹤區段（span）記錄中與追蹤群組相關的欄位。它也會擴充來自生成式 AI（GenAI）代理程式與大型語言模型（LLM）應用程式的追蹤資料。如需詳細資訊，請參閱[GenAI 代理程式追蹤擴充](#genai-agent-trace-enrichment)。

此處理器先前名為 `otel_trace_raw`。您仍可使用 `otel_trace_raw` 名稱，但該名稱已棄用，並預計在 Data Prepper 3.0 中移除。
{: .note}

## 使用方式

此處理器會將下列欄位新增至追蹤區段 (span) 事件：

* `traceGroup`：根追蹤區段名稱
* `endTime`：整個追蹤的結束時間，採用國際標準化組織 (ISO) 8601 格式
* `durationInNanos`：整個追蹤的持續時間，以奈秒為單位
* `statusCode`：整個追蹤的狀態碼

## GenAI 代理程式追蹤擴充

`otel_traces` 處理器會擴充來自 GenAI 代理程式與 LLM 應用程式的追蹤，讓您能直接從追蹤區段（span）本身尋找、列出及衡量代理程式的執行，例如在 OpenSearch Dashboards 的 **Agent Traces** 頁面中。擴充功能預設為開啟，適用於 Data Prepper 2.14 及更新版本，且不會變更不含 GenAI 資料的追蹤。

擴充功能會依 OpenTelemetry（OTel）的鍵名稱比對屬性，例如 `gen_ai.operation.name`，因此來源必須以 OTel 格式發出追蹤區段。[`otel_trace_source`]({{site.url}}{{site.baseurl}}/data-prepper/pipelines/configuration/sources/otel-trace-source/) 來源預設使用 `opensearch` 格式，因此請將其 `output_format` 設為 `otel`。[`otlp`]({{site.url}}{{site.baseurl}}/data-prepper/pipelines/configuration/sources/otlp-source/) 來源預設使用 `otel` 格式。`opensearch` 格式會改寫屬性鍵（例如 `http.method` 會變成 `span.attributes.http@method`），導致擴充功能找不到任何 GenAI 資料。
{: .important}

對於批次中的每個追蹤，處理器會依序套用下列步驟：

1. [廠商屬性正規化](#vendor-attribute-normalization)
1. [移除扁平化子鍵](#flattened-sub-key-stripping)
1. [根追蹤區段擴充](#root-span-enrichment)
1. [代理程式根標記](#agent-root-marker)

若要關閉所有這些步驟，請將 `disable_genai_enrichment` 設為 `true`。如此一來，追蹤區段屬性會維持接收時的原樣，且處理器不會建立任何涵蓋範圍快取。

### 廠商屬性正規化

不同的檢測程式庫會以不同名稱表示相同的資料。例如，輸入詞元在 OpenInference 中為 `llm.token_count.prompt`，在 OpenLLMetry 中為 `llm.usage.prompt_tokens`，在 [OTel GenAI 語意慣例](https://opentelemetry.io/docs/specs/semconv/gen-ai/)中則為 `gen_ai.usage.input_tokens`。此處理器會將廠商屬性複製為對應的 `gen_ai.*` 名稱，讓查詢、儀表板及其餘擴充處理只需使用標準名稱。正規化遵循下列規則：

* 對應列於 [`genai-attribute-mappings.yaml`](https://github.com/opensearch-project/data-prepper/blob/main/data-prepper-plugins/otel-trace-raw-processor/src/main/resources/genai-attribute-mappings.yaml) 中，並依來源分組：`openinference`、`openllmetry`（Traceloop）及 `claude_code`。
* 原始屬性會保留，`gen_ai.*` 副本會新增在原始屬性旁。
* 追蹤區段（span）上已存在的 `gen_ai.*` 屬性永遠不會被覆寫。
* 當同一個追蹤區段上有多個屬性對應到相同的 `gen_ai.*` 名稱時，會使用對應檔案中最先列出的屬性。例如，OpenInference 的 `session.id` 屬性會優先於 Traceloop 的 `traceloop.association.properties.session_id` 使用；兩者皆對應到 `gen_ai.conversation.id`。
* 操作類型會對應到 `gen_ai.operation.name` 值。例如，OpenInference 的 `LLM` 類型會變成 `chat`，`AGENT` 和 `CHAIN` 會變成 `invoke_agent`，而 `TOOL` 會變成 `execute_tool`。
* 部分對應會將單一值包裝在 JSON 陣列中，例如 `gen_ai.response.finish_reasons` 中的完成原因。

從 Data Prepper 2.17 開始，Traceloop 工作階段 ID（`traceloop.association.properties.session_id`）會對應到 `gen_ai.conversation.id`，藉此將追蹤分組為工作階段。

### 移除扁平化子鍵

部分檢測工具會將同一個欄位輸出兩次：一次為 JSON 字串（例如 `llm.input_messages`），一次為扁平化子鍵（例如 `llm.input_messages.0.message.content`）。OpenSearch 會因對應衝突而拒絕這類文件。當父字串存在時，處理器會移除已編製索引的子鍵。當只有子鍵存在時，則會保留這些子鍵，以免遺失任何資料。

### 根追蹤區段擴充

處理器可以將 `gen_ai.system`、`gen_ai.provider.name`、`gen_ai.agent.name`、`gen_ai.request.model` 以及追蹤的詞元總數，從子追蹤區段 (span) 複製到該追蹤的根追蹤區段。根追蹤區段原本已有的屬性會予以保留。系統會先從最外層的 GenAI 追蹤區段取值（依最早開始時間排序），接著從其他 GenAI 追蹤區段取值，最後再從其餘子追蹤區段取值。

`genai_root_propagation` 選項用於選擇哪些根追蹤區段會接收複製的資料，如下表所述。

值 | 接收複製資料的根追蹤區段
:--- | :---
`ai_root`（預設） | 僅限屬於其追蹤之 AI 根的根追蹤區段：也就是 GenAI 追蹤區段，或在來源端標記為 `derived.gen_ai.is_root: true` 的追蹤區段。
`all_roots` | 所有根追蹤區段，包括非 GenAI 的根追蹤區段，例如代理程式在其後方執行的 HTTP 追蹤區段。這是 Data Prepper 2.17 之前的預設值。
`none` | 不套用至任何根追蹤區段。

使用 `ai_root` 時，非 GenAI 根追蹤區段只會保留其本身的屬性。若將代理程式資料複製到非 GenAI 根追蹤區段，會使 HTTP 追蹤區段看起來像是呼叫了模型並使用了詞元、將平行執行的代理程式合併為單一代理程式名稱，而且對於任何跨追蹤區段加總用量的取用端，會重複計算該追蹤的詞元。這些資料改由[代理程式根標記](#agent-root-marker)追蹤區段承載。

標記功能不受此選項影響：使用 `none` 時，處理器所標記的代理程式追蹤區段仍會接收其子系追蹤區段的詞元總數。

在 Data Prepper 2.17 中，預設行為已從複製到所有根追蹤區段變更為 `ai_root`。如果您的查詢或儀表板會從非 GenAI 根追蹤區段讀取代理程式資料（例如 `gen_ai.agent.name` 或詞元總數），請將 `genai_root_propagation` 設定為 `all_roots` 以保留先前的行為，或改從已標記的代理程式追蹤區段讀取資料。
{: .important}

### 代理程式根標記

代理程式通常在服務後方執行：追蹤的根追蹤區段 (span) 是 HTTP 或 RPC 追蹤區段，例如 `POST /plan`，而代理程式追蹤區段則巢狀位於其下。因此，依根追蹤區段列出追蹤的取用端會遺漏代理程式，或改為顯示 HTTP 追蹤區段。從 Data Prepper 2.17 開始，處理器會以 `derived.gen_ai.is_root: true` 標記代表每次代理程式執行的追蹤區段。此標記遵循下列規則：

* 每個追蹤中最外層的 GenAI 追蹤區段都會被標記。這是指具有 `gen_ai.operation.name` 且沒有 GenAI 祖先的追蹤區段：可能是根追蹤區段本身（當它是 GenAI 追蹤區段時），或是巢狀位於非 GenAI 根之下的代理程式追蹤區段。
* 當多個頂層代理程式在同一個根追蹤區段下執行時，每個代理程式都會被標記為一次代理程式執行。
* 在代理程式呼叫代理程式的鏈結中，例如 `invoke_agent` > HTTP 用戶端 > HTTP 伺服器 > `invoke_agent`，只有發出呼叫的代理程式會被標記，因為被呼叫的代理程式具有 GenAI 祖先。
* 由處理器標記且本身未回報任何詞元用量的追蹤區段，會取得其後代的用量。在來源端標記的追蹤區段不會取得這些總計。後代用量的計算方式如[詞元用量](#token-usage)所述。
* SDK 或使用者可以在來源端為追蹤區段設定此標記。如果追蹤中有任何追蹤區段在來源端被標記為 `true`，處理器就不會標記該追蹤中的其他追蹤區段。設定為 `false` 的追蹤區段永遠不會被標記，因此在追蹤最外層的 GenAI 追蹤區段上設定 `false`，即可將該追蹤排除在標記之外。
* 在 `trace_flush_interval` 之後未連同根追蹤區段一起排清的追蹤區段仍會被標記，因為此標記只需要該追蹤區段的後代。

若要列出追蹤的代理程式執行，請查詢其已標記的追蹤區段。對於在此標記出現之前即已編製索引的資料，請改為查詢屬於 GenAI 追蹤區段的根追蹤區段。

#### 延遲抵達的追蹤區段與涵蓋範圍快取

同一個追蹤的追蹤區段 (span) 可能分成多個批次抵達。若某個追蹤區段在其代理程式追蹤區段處理完成後才抵達，系統會在沒有其祖系追蹤區段的情況下擴充該追蹤區段，因此它看起來會像是最外層的追蹤區段，並被標記為第二次代理程式執行。為了避免這種情況，處理器會針對每個追蹤，記錄哪些追蹤區段 ID 已由 GenAI 追蹤區段或標記涵蓋，並在追蹤區段的父項不在批次中時檢查此記錄。涵蓋範圍快取的運作方式如下：

* 項目的保留時間為 `trace_flush_interval` 的兩倍加上 `trace_group_cache_ttl`（預設為 375 秒），因此保留時間會比未隨根追蹤區段一起抵達之追蹤區段的排清時間更長。
* 快取在所有追蹤中最多儲存 `genai_coverage_cache_max_size` 個追蹤區段 ID。只會儲存包含 GenAI 追蹤區段的追蹤。`genAiCoverageSpanIdCount` 指標會以追蹤區段 ID 數量回報快取的使用量。
* 快取每秒約可支援 `genai_coverage_cache_max_size` / (2 × `trace_flush_interval` + `trace_group_cache_ttl`) 個 GenAI 追蹤區段，預設約為每秒 1,300 個追蹤區段。速率較高時，追蹤會提早被逐出，延遲抵達的追蹤區段可能會再次被標記，因此若 GenAI 追蹤區段的速率較高，請增加 `genai_coverage_cache_max_size`。
* 已涵蓋追蹤區段的查詢、標記和更新會針對每個追蹤以不可分割的方式執行，因此同時處理同一追蹤之追蹤區段的多個管線工作者，不會都標記同一個追蹤區段。

涵蓋範圍快取有以下限制：

* 若追蹤區段在其所屬追蹤的項目已過期或已被逐出之後才抵達，則可能會被標記。
* 若追蹤的子追蹤區段在 GenAI 根追蹤區段抵達之前就已排清，則根追蹤區段和最外層的子追蹤區段都可能被標記。取用者應優先採用沒有父項的已標記追蹤區段。
* 若受呼叫服務的追蹤區段在 `trace_flush_interval` 之後排清，且未包含呼叫端的追蹤區段，則受呼叫的代理程式也會被標記，並列為另一次獨立的代理程式執行。

### 詞元用量

當處理器加總 `gen_ai.usage.input_tokens` 和 `gen_ai.usage.output_tokens` 時，無論是加總至根追蹤區段 (span) 或已標記的代理程式追蹤區段，都只會計入沒有任何同樣回報用量之上層追蹤區段的追蹤區段。`invoke_agent` 等代理程式追蹤區段通常會回報其本身 LLM 呼叫的總和，因此若將每個回報用量的追蹤區段都相加，這些呼叫就會被重複計算。詞元計數遵循下列規則：

* 上層追蹤區段回報的用量會被視為已包含其子樹。在僅回報自身用量的父項之下執行自身 LLM 呼叫的子代理程式，不會被加計。
* 回報任一詞元計數的追蹤區段會被視為有回報用量，並保留其本身的值。
* 以數值字串傳送的詞元計數會被讀取為數字。其他值則會被忽略。

### 範例

以下管線會接收 OTel 格式的 OpenTelemetry Protocol (OTLP) 追蹤，並將擴充後的追蹤區段 (span) 寫入 OpenSearch。GenAI 選項以其預設值顯示：

```yaml
otel-traces-pipeline:
  source:
    otel_trace_source:
      ssl: false
      output_format: otel
  processor:
    - otel_traces:
        disable_genai_enrichment: false
        genai_root_propagation: ai_root
        genai_coverage_cache_max_size: 500000
  sink:
    - opensearch:
        hosts: ["https://opensearch:9200"]
        index_type: trace-analytics-plain-raw
```

## 指標

下表說明常見的[抽象處理器](https://github.com/opensearch-project/data-prepper/blob/main/data-prepper-api/src/main/java/org/opensearch/dataprepper/model/processor/AbstractProcessor.java)指標。

| 指標名稱 | 類型 | 說明 |
| ------------- | ---- | -----------|
| `recordsIn` | 計數器 | 表示記錄流入管線元件的指標。 |
| `recordsOut` | 計數器 | 表示記錄從管線元件流出的指標。 |
| `timeElapsed` | 計時器 | 表示管線元件執行期間所經過時間的指標。 |

`otel_traces` 處理器包含下列自訂指標：

* `traceGroupCacheCount`：追蹤群組快取中的追蹤群組數量。
* `spanSetCount`：追蹤區段組集合中的追蹤區段 (span) 組數量。
* `genAiCoverageCount`：GenAI 涵蓋範圍快取中的追蹤數量。
* `genAiCoverageSpanIdCount`：GenAI 涵蓋範圍快取中的追蹤區段 ID 數量，單位與 `genai_coverage_cache_max_size` 相同。適用於 Data Prepper 2.17 及更新版本。
