# Logstash 執行模型

Logstash 在輸入執行緒上接收事件、將其排入佇列，並在管線工作執行緒上分批處理。工作執行緒的數量與每個批次的大小，決定了 Logstash 平行處理的事件數量，以及每個事件送達目的地的速度。

## 並行處理事件

Logstash 管線可以從多個輸入接收事件。每個輸入都在各自的執行緒中執行，因此輸入之間不會互相封鎖。如果兩個事件同時抵達，Logstash 會並行接收這兩個事件。

輸入接收到事件並套用其編解碼器（若有）之後，Logstash 會將事件加入工作佇列。_管線工作執行緒_（_pipeline workers_，或稱 _批次處理器_、_batchers_）會從佇列取出事件，並執行篩選器、輸出及輸出編解碼器。每個管線工作執行緒都在各自的執行緒中執行，因此 Logstash 會同時處理多個事件。

## 批次處理事件

管線工作執行緒會從工作佇列中批次取出事件。批次處理可提升輸送量，原因如下：

- 部分處理無論事件數量多寡都必須執行一次。對一批 100 個事件執行一次，比執行 100 次更有效率。
- 部分輸出外掛程式會以群組方式傳送事件。例如，OpenSearch 輸出外掛程式會將每批事件透過單一 Bulk API 請求傳送至 OpenSearch。

有兩項設定決定管線工作執行緒何時處理批次：批次大小上限與批次延遲。當批次達到大小上限，或批次延遲時間已過，工作執行緒就會處理該批次，以先發生者為準。例如，若批次大小上限為 50、批次延遲為 100 ms，則工作執行緒會在批次包含 50 個事件時，或開始收集事件後 100 ms 時，立即處理該批次。

批次延遲可確保事件量較少的管線也能處理事件，而不會長時間延遲。例如，若管線將網頁伺服器錯誤記錄檔傳送至 OpenSearch，可能需要很長時間才能收集到 50 個事件。由於有批次延遲，這些錯誤會在幾毫秒內顯示於 OpenSearch Dashboards。

預設值適用於大多數管線。只有在需要調整管線效能時才變更這些值。

## 管線工作執行緒與 CPU 核心

只有在有足夠的 CPU 核心時，管線工作執行緒才能平行處理事件。例如，如果您在只有 2 個 CPU 核心的伺服器上執行 5 個工作執行緒，這些工作執行緒會爭搶核心。如果您在具有 10 個 CPU 核心的伺服器上執行 5 個工作執行緒，則有一半的核心不會用於事件處理。

預設情況下，Logstash 會將管線工作執行緒的數量設定為主機上的 CPU 核心數。由於 Logstash 是在啟動時決定這個數字，因此您不需要為核心數不同的主機（例如開發用電腦與正式環境伺服器）分別設定 Logstash。

## 設定

下表列出控制管線工作執行緒與批次處理的設定。請在 `config/logstash.yml` 檔案中指定這些設定，或在啟動 Logstash 時以命令列引數傳入。

設定 | 命令列引數 | 說明
:--- | :--- | :---
`pipeline.workers` | `-w` | 管線工作執行緒的數量。預設為主機上的 CPU 核心數。
`pipeline.batch.size` | `-b` | 管線工作執行緒在處理事件前所收集的事件數量上限。預設為 `125`。
`pipeline.batch.delay` | `-u` | 管線工作執行緒在處理尚未達到大小上限的批次前，等待新事件的時間（毫秒）。預設為 `50`。

例如，下列命令會以 4 個管線工作執行緒及 250 的批次大小上限啟動 Logstash：

```bash
bin/logstash -f config/pipeline.conf -w 4 -b 250
```
